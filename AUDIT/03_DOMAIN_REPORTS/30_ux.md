### Error boundaries (route-level)
Capability: an unhandled error on a specific page shows a friendly, on-brand error state (not a
white screen or a raw stack trace), with a retry.
Status: PARTIAL
Evidence: EV-6023
Files: src/app/error.tsx (10 lines, full); src/app/renewals/error.tsx (only other route-level
error.tsx among 109 page.tsx files); src/components/ErrorState.tsx (full, 40+ lines)
Functions/classes: RouteError, ErrorState
Observed behavior: the root `error.tsx` is well-built — Arabic message, a "digest" reference code
for support (never a raw stack trace to the user, per the code comment: "Never shows stack traces"),
a retry button (`reset`), and a home link. Per Next.js App Router conventions, this root
`error.tsx` **does** catch errors from any page that does not have its own closer `error.tsx` (React
error boundaries bubble to the nearest ancestor), so the practical coverage is better than "2 of 109
pages" sounds — every page not opting out of the default is still caught by the root boundary. Only
`/renewals` has a page-specific override.
Missing pieces: because there is only one specialized `error.tsx` (renewals), no page can show a
more specific, contextual error message (e.g. "your leave request could not be calculated" vs. the
generic "حدث خطأ غير متوقع") — verified by absence: no other `error.tsx` found under `src/app/portal`,
`src/app/manager-portal`, `src/app/dept-manager`, etc. This means a crash within a specific ESS/MSS
flow shows only the generic message, losing context on what actually failed.
Risk: Low-Medium (functional coverage exists via the root boundary; the gap is message
specificity/UX polish, not a broken/missing capability).
Confidence: High

### Loading states (route-level)
Capability: navigating to a page shows a loading indicator instead of a blank screen while data
loads.
Status: PARTIAL
Evidence: EV-6023
Files: src/app/loading.tsx (10 lines, full, Arabic spinner with `role="status" aria-live="polite"`
— accessible)
Observed behavior: same bubbling logic as error.tsx applies — the single root `loading.tsx` is
Next.js's Suspense boundary fallback for the whole route tree unless a page defines its own,
meaning it likely does cover navigation between top-level routes reasonably (Next.js shows it while

spinner (`isLoading` state + a full local skeleton) rather than relying on the file-convention

some places, ad hoc component state in others), which is a maintainability/consistency concern
rather than a missing-capability one.
Missing pieces: no per-route `loading.tsx` beyond the root; loading-state pattern is not
standardized across the 109 pages.
Risk: Low.
Confidence: Medium (pattern inferred from the one page read in depth; not verified across all 109
page.tsx files)

### Fetch-target integrity (buttons/pages that call APIs that do not exist)
Capability: no page calls an API endpoint that isn't actually implemented (the "looks implemented
but doesn't work" pattern the brief calls out).
Status: COMPLETE (for the sample obtained)
Evidence: EV-6025
Files: all `.tsx` under `src/app` (71 distinct literal `fetch('/api/...')` targets extracted);
`src/app/api/**/route.ts` (149 route files)
Observed behavior: every one of the 71 literal-string fetch targets resolves to an existing
`route.ts`, including dynamic-segment matches (e.g. a literal prefix that is actually a dynamic
route's static parent). No orphaned fetch call was found in the sample.
Missing pieces: this method only catches **string-literal** fetch calls
(`fetch('/api/...')`); it does not catch template-literal targets
(`` fetch(`/api/leaves/${id}/action`) ``), which are common for per-id and per-action endpoints
(e.g. the leave-cancel call in Domain 11's report uses exactly this pattern:
`` fetch(`/api/leaves/${encodeURIComponent(leaveId)}/action`) ``). Those were spot-verified
individually during the Domain 11/12 file reads (all found to resolve to real routes), but a
codebase-wide reconciliation of template-literal fetches was not performed — this is a coverage
limitation of the method, not a confirmed absence of orphaned calls elsewhere in the other 7
domains' pages.
Risk: Low (no orphan found; residual risk is method coverage, not a confirmed gap).
Confidence: Medium (71 of an unknown larger total of all fetch call sites, since template-literal
calls were not counted)

### Pagination on request/queue lists
Capability: long lists (pending requests, history feeds) are paginated rather than growing
unbounded.
Status: PARTIAL
Evidence: EV-6026
Files: src/app/api/incoming-requests/route.ts (multiple `findMany` calls for pending queues with no
`take`/`skip`, grep confirmed at lines 240, 283, 289, 295, 301, 307, 313, 328, 334, 342, 348, 361 —
none show a `take:` parameter in the surrounding context checked); src/app/api/manager-portal/route.ts:107-150
(`get_history`, explicitly capped with `HISTORY_TAKE = 10` per sub-query and `.slice(0, 50)` overall
— a contrasting, correctly-bounded example in the same domain)
Observed behavior: the manager-portal history feed (Domain 12) is deliberately capped
(`HISTORY_TAKE`, `.slice(0,50)`); the HR-facing incoming-requests pending-approval queues, by
contrast, have no visible cap in the route handler — every pending row of every type is returned in
one response. For a queue of genuinely "pending" items this is often self-limiting in practice
(pending counts stay small because items get approved/rejected), but there is no defensive cap, so
a backlog (e.g. after a period without HR review) could return an unbounded, unpaginated payload.
Missing pieces: no `take`/cursor pagination on the incoming-requests pending lists.
Risk: Low-Medium (a real but low-likelihood scaling gap, not a security issue; degrades gracefully
as slow UI rather than failing).
Confidence: Medium (based on the specific `findMany` call sites grepped; full route logic not read
end-to-end)

## Edge cases checked

- **Account with no linked employee record opening `/portal`**: shows `UnlinkedAccountCard`, not a
  crash or blank page (page.tsx:325-339, 526-534). Finding: handled (also noted in Domain 11).
- **Server error mid-page-load vs. mid-form-submit**: page-load failures show a dedicated
  full-page error state with retry (`loadError` branch, page.tsx:508-524); form-submit failures show
  a toast and leave the form open for correction (e.g. handleLeaveSubmit) — two different, both
  appropriate, patterns for two different failure moments. Finding: handled correctly, differentiated
  by context.
- **Rapid double-submit of a form (e.g. leave request)**: client-side guarded by a `submitting`
  state flag checked at the top of every handler (`if (submitting) return`, e.g. page.tsx:565, 596,
  647, 689, 734) in addition to the server-side transactional locks found in Domains 11/12. Finding:
  handled at both layers (defense in depth, not merely client-side).
- **A pending-requests queue growing large over time (HR backlog)**: no pagination cap found on the
  incoming-requests read side. Finding: gap (see "Pagination on request/queue lists" above). EV-6026.
- **A crash inside a specific ESS/MSS flow (not page load)**: falls back to the generic root
  `error.tsx` message rather than a flow-specific one, since only `/renewals` has its own
  `error.tsx`. Finding: functionally covered, message specificity is a polish gap. EV-6023.
