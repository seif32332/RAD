## Edge cases checked

- **Duplicate/double-click approval**: guarded by the `updateMany` count===0 pattern everywhere reviewed (`hr-workflows.ts`, `incoming-requests/route.ts`) - EV-8003/8004. Finding: handled correctly across every module checked.
- **Legacy `PaymentRequest` rows with no known `requestedById`**: `decideMakerChecker` has an explicit `UNKNOWN_REQUESTER` basis, allowed but distinctly flagged (not silently treated as "different user") - EV-8007 (`x-security-maker-checker.test.ts` case "allows legacy rows without a requester, flagged as unknown").
- **Email send outcome ambiguity (SMTP timeout mid-DATA command)**: classified `UNKNOWN`, never auto-retried, to avoid a possible duplicate send - EV-8018 (`classifySendError`, `jobs.mjs:254-263`). Correctly conservative.
- **Recipient deactivated/terminated between digest enqueue and dispatch**: `outboxDispatch` re-checks `User.isActive` and `Employee.isTerminated` for `expiry-digest:` rows immediately before send and marks them `FAILED` with `lastError: 'recipient no longer active'` rather than sending - EV-8019 (`jobs.mjs:541-547`). Not verified for the document-engine notice producers (their idempotency keys don't match the `expiry-digest:` regex, so this re-check does **not** apply to them - flagged as a gap, not confirmed exploited).
- **Arabic/RTL text in notifications**: all notification bodies observed are plain-text Arabic (no HTML), so RTL rendering is delegated to the mail client by Unicode bidi rules rather than explicit `dir="rtl"` markup - no defect found because no HTML is sent in this domain's code paths (EV-8027).
