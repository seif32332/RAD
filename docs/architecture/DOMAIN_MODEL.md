# 1. نموذج النطاق (Domain Model)

## 1.1 ثلاثة أنواع من السجلات فقط

كل جدول في رديف ينتمي لنوع واحد من هذه الثلاثة، ويُكتب نوعه في تعليق النموذج في `schema.prisma` (`/// kind: FACT | REQUEST | PROJECTION`).

| النوع | التعريف | أمثلة | قواعد الكتابة |
|---|---|---|---|
| **FACT (حقيقة)** | ما هو صحيح عن العالم، مؤرخ إن كان يتغير عبر الزمن | فترة التوظيف، فترة الأجر، فترة التعيين، سطر مسير معتمد، حركة رصيد إجازة، بصمة | تُكتب فقط بدالة الانتقال المالكة، ولا تُحذف ولا تُعدَّل بعد الاعتماد (تُلغى بسجل عكسي أو فترة لاحقة) |
| **REQUEST (طلب أو قرار)** | نية تغيير تمر بموافقة | طلب إجازة، `EmployeeFinancialChange` (طلب تغيير مالي، PAY)، `EmployeeChangeOrder` (قرار مؤرخ)، طلب نقل، طلب قرض | الموافقة **تنتج FACT**، والطلب نفسه لا يكون مصدر حقيقة لأي رقم |
| **PROJECTION (إسقاط)** | نسخة محسوبة للقراءة السريعة | `Employee.basicSalary`، `Employee.branchId`، `isTerminated`، لوحات التقارير | يكتبها **المُسقِط** (projector) وحده في نفس معاملة الحقيقة أو من الحدث. ويمكن إعادة بنائها من الحقائق في أي وقت. وأي كتابة أخرى عليها مخالفة ARCH-011 |

**الحقائق التي يُضاف إليها لا تُحذف صفوفها** (ADR-0002 #13): العكس صف أو مراجعة بمرجع (`reversesId`)، مثل مراجعات لقطة المسير (`LEGACY`، `REVERSAL`، `BANK_REISSUE`؛ #11) ودفتر الإجازة.

**القاعدة الذهبية:** الأرقام تُقرأ من FACT (أو من PROJECTION مضمون مطابقتها بثابت)، ولا تُقرأ أبداً من REQUEST.

> **تصحيح لتسمية PAY:** `EmployeeFinancialChange` في تصميم PAY طلب (PENDING ← APPLIED أو REJECTED). تطبيقه **ينشئ فترة أجر نافذة** (`CompensationPeriod`)، وهي الحقيقة. لا يُقرأ الراتب من الطلب ولا من `Employee.basicSalary` مباشرة في أي حساب مالي.

## 1.2 الكيانات الأساسية المستهدفة

| الكيان | النوع | الوحدة | الوصف |
|---|---|---|---|
| `Employee` | هوية + إسقاطات | people | الهوية الثابتة (الاسم، الجنسية، الهوية، تاريخ الميلاد). أعمدة الراتب والتعيين والحالة عليه **إسقاطات** فقط |
| `EmploymentPeriod` | FACT مؤرخ | lifecycle | من تاريخ المباشرة إلى آخر يوم عمل. فترة واحدة مفتوحة كحد أقصى. إعادة التعيين تفتح فترة جديدة (LCY T4) |
| `EmploymentStateChange` | FACT (لا يُعدَّل ولا يُحذف) | lifecycle | **هو حقيقة الحالة** (DEC-PO-119): كل انتقال (ACTIVE ← NOTICE ← TERMINATED …) بتاريخ نفاذه وسببه (قاموس `ExitReason` واحد) وفاعله ومفتاح العملية. `Employee.employmentState` إسقاط = `to` لآخر تغيير غير مستبدل بترتيب التسجيل، تكتبه نفس الدالة في نفس المعاملة |
| `BankIdentityPeriod` | FACT مؤرخ (جديد) | compensation | الآيبان مشفراً، والبصمة، وآخر 4، والبنك، وطريقة الدفع. validFrom = تاريخ التطبيق، ولا تُؤرَّخ رجعياً أبداً (ADR-0001 #8) |
| `CompensationPeriod` | FACT مؤرخ (جديد) | compensation | الأساسي والسكن والنقل والبدلات الثابتة وأساس GOSI وتجاوزاته، لفترة نافذة |
| `AssignmentPeriod` | FACT مؤرخ (جديد) | org | الشركة النظامية، والشركة الفعلية، والفرع، والقسم، والمدير المباشر، والمنصب، ومركز التكلفة، ونمط العمل |
| `GosiRegistrationPeriod` | FACT مؤرخ (جديد) | payroll | النظام (قديم أو جديد)، والمنشأة، وتاريخ التسجيل، لكل فترة توظيف |
| `ContractPeriod` | FACT مؤرخ | lifecycle | نوع العقد، وتاريخ البداية والنهاية، والتجديدات، والتجربة. محدد المدة يُشتق من وجود تاريخ نهاية |
| `WorkPattern` + `HolidayCalendar` | إعداد مؤرخ | time | أيام العمل والراحة والساعات، والعطل الرسمية، وفترة رمضان |
| `DayRecord` | FACT (جديد) | time | حالة يوم واحدة لكل موظف ويوم عمل مجدول في فترة مغلقة (INV-ATT-01) |
| `LeaveLedgerEntry` | FACT | leave | حركة رصيد: استحقاق، أخذ، صرف نقدي، تسوية، ترحيل، سقوط |
| `PayrollMonth` / `PayrollLine` | FACT بعد الاعتماد | payroll | مسير لكل شركة لكل شهر، وسطر لكل موظف، مع لقطة مدخلات كاملة |
| `ExitCase` | FACT + حالة | offboarding | ملف الخروج (OFF) |
| `WorkflowInstance` / `WorkflowTask` | حالة | workflow | محرك الموافقات (WFE) |
| `DomainEvent` | FACT (outbox) | platform | حدث بعد كل انتقال |
| `NotificationOutbox` | FACT + حالة | platform | رسالة واحدة بقناة، مع `expiresAt`. والمستهلك يعيد التحقق من صلاحيتها قبل الإرسال (ADR-0001 #13) |
| `Discrepancy` | FACT + حالة | platform | اختلاف اكتشفته المصالحة (ARCHITECTURE_INVARIANTS §3) |

## 1.3 الزمن: الفترة النافذة (Effective Period)، البدائية المركزية

كل معلومة تتغير عبر الزمن وتؤثر على مال أو حق أو قانون **يجب** أن تُخزَّن فترات نافذة، لا عموداً يُعدَّل في مكانه:

**يشمل ذلك:** الراتب والبدلات، والشركة، والفرع، والقسم، والمدير، والمنصب، ومركز التكلفة، ونمط العمل، ونظام GOSI، والعقد، والتوظيف نفسه، وسياسة الإجازة لكل شركة، والقيم القانونية (`RuleParameter`).

### الشكل الموحد

```text
<Entity>Period
  id
  subjectId          -- الموظف (أو الشركة لقواعدها)
  validFrom  DATE    -- أول يوم نفاذ (شامل)، تقويم الرياض، مخزن منتصف ليل UTC
  validTo    DATE?   -- أول يوم بعد النهاية (حصري)؛ NULL = مفتوحة
  recordedAt TIMESTAMP  -- متى عرف النظام بها (زمن التسجيل)
  supersededAt TIMESTAMP? / supersededById  -- إن صُححت الفترة بفترة بديلة (لا حذف)
  sourceType / sourceId  -- القرار أو الطلب الذي أنتجها (ChangeOrder, FinancialChange, ExitCase…)
  createdById
```

### قواعد ملزمة (تُفرض بقيود قاعدة البيانات وتُختبر)

1. **لا تداخل:** لكل (subject، نوع) لا توجد فترتان فعّالتان (غير مستبدلتين) متقاطعتان. يُفرض بقيد `EXCLUDE USING gist (subjectId WITH =, daterange(validFrom, validTo) WITH &&) WHERE supersededAt IS NULL` في Postgres، مع إضافة `btree_gist` بترحيل.
2. **لا فجوة غير مبررة:** داخل فترة توظيف مفتوحة يجب أن تغطي فترات الأجر والتعيين كل يوم. الفجوة مسموحة فقط لنوع صريح (مثل إجازة بلا أجر ممتدة)، ويفحصها INV-EFF-02.
3. **سجل نشط واحد في أي تاريخ:** `activeAt(subjectId, date)` يعيد صفراً أو واحداً، ولا أكثر.
4. **لا تعديل رجعي في المكان:** تصحيح فترة ماضية = استبدالها (`supersededAt`) بفترة جديدة. التاريخ الأصلي يبقى، فيمكن الإجابة عن "كم كان الراتب في 15 أغسطس **كما عرفناه عند اعتماد مسير أغسطس**".
   - **الاستثناء الوحيد المسمى** (ADR-0001 #9، DEC-PO-043): نهاية فترة التوظيف `EmploymentPeriod.validTo` تُعدَّل في مكانها، بما في ذلك إعادتها NULL عند إعادة الفتح، بدالة lifecycle وحدها، ويُسجَّل كل تعديل في `EmploymentStateChange`. معرّف الفترة ثابت، وتصحيح بدايتها استبدال.
   - **الإبطال** (ADR-0002 #3) = `supersedePeriod` بلا خلف بسبب VOID، ولا يوجد عمود `voidedAt`. واستبدال `EmploymentStateChange` يكون بصف جديد يحمل `supersedesId`.
   - **القراءة "كما سُجّلت" لنهاية التوظيف** (ADR-0002 #4): `effectiveContext(..., {asRecordedAt: T})` يشتق نهاية فترة التوظيف من تغييرات الحالة المسجلة حتى T، لا من العمود.
   - **معرّف السلالة** (ADR-0002 #12): لكل فترة نافذة `lineageId` ثابت يرثه كل خلف في الاستبدال، والمراجع الخارجية تشير إلى السلالة لا إلى الصف. السلالة سلسلة استبدال فقط، وإعادة التعيين تبدأ سلالة جديدة.
5. **دالة واحدة لكل نوع:** `openPeriod` و`closePeriod` و`supersedePeriod` في `src/modules/platform/effective/`، تستعملها كل الوحدات، ولا وحدة تكتب جدول فترات بـPrisma مباشرة (ARCH-012).

### السياق النافذ (Effective Context)

```ts
effectiveContext(employeeId, date, { asRecordedAt? }) → {
  employment: EmploymentPeriod,       // هل هو في الخدمة؟ أي فترة؟
  state: 'ACTIVE' | 'NOTICE' | ...,
  assignment: { legalCompanyId, actualCompanyId, branchId, departmentId, managerId, positionId, costCenterId, workPatternId },
  compensation: { basic, housing, transport, fixedAllowances[], gosiBase },
  gosi: { regime, establishmentId },
  contract: { type, endDate, probationEnd },
  dayType: 'WORK' | 'REST' | 'HOLIDAY' | 'RAMADAN_WORK' | ...
}
```

- **المسير** يحسب كل يوم من أيام الشهر بـ`effectiveContext(e, d, { asRecordedAt: now })`، فيعالج منتصف الشهر تلقائياً.
- **الأثر الرجعي** = الفرق بين حساب الشهر المعتمد (من لقطته، أي `asRecordedAt = وقت الاعتماد`) وحسابه الآن. **مكوّن الإجازة:** تُجمَّد بنود LEAVE على قيم اللقطة، وفروقها تمر فقط عبر `LeaveAdjustmentCase` في payroll (ADR-0002 #7، WF-LEV-002). الفرق يُدفع أو يُستقطع كسطر فرق في أول شهر مفتوح، ولا يُعدَّل شهر معتمد.
- **التقارير** و**الحضور** و**الإجازات** و**نطاقات** تستخدم نفس الدالة.

## 1.4 المال

- كل مبلغ يُحسب ويُخزَّن **بالهللة** عبر `money.ts` (`roundMoney` و`sumMoney`) إلى حين ترحيل الأعمدة إلى `Decimal(14,2)` (خطة P6-MONEY). لا عملية حسابية على مبالغ خارج هذه الدوال (ARCH-013).
- التقريب يحدث مرة واحدة في نقطة محددة لكل بند (سطر المسير، بند التسوية). وفروق التقريب المتوقعة تُصنف `EXPECTED` في المصالحة، لا اختلافاً.
- كل مبلغ مالي معتمد يحمل **لقطة مدخلاته** (المعدل، الأساس، الأيام، القاعدة ونسختها)، فيمكن إعادة حسابه وشرحه.

## 1.5 الهوية والملكية

- كل كيان تشغيلي يحمل `companyId` صريحاً (الشركة النظامية المالكة)، أو يُشتق نطاقه عبر FK موثق في DOMAIN_BOUNDARIES §4. **لا كيان تشغيلي بلا نطاق شركة معروف.**
- المعرّفات UUID. والمراجع بين الجداول FK حقيقية (لا نص يحوي معرّفاً، ولا ربط بمطابقة اسم).
- حقول الفاعل: `createdById`، و`decidedById`/`approvedById`، و`paidById`، كلها FK إلى `User` مع `onDelete: Restrict`.
- حالة كل كيان عمود enum أو CHECK، ولا نص حر.
